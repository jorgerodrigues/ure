# Edit queue verification

Recorded on 6 November 2026 for the edit queue, a structural change between W040 and W041 with no GitHub issue. On 6 November the user asked to "fix the root cause" of the save-order and Undo bugs that Codex found in every Rework story, instead of patching them one by one. The branch started at `aebd6c2` on `w002-recoverable-library`, which includes W033 to W040. The latest migration there is `v26-parts`. This change adds no migration. The one thing it changes on screen is how a failed save shows: once, for the whole window, instead of under each field.

## The root cause

Before this change each of 16 autosave fields ran its own pause and its own save task, each of 12 `ChangeUndo` queues ordered only one kind of change, and about 30 `pendingWrites` and `isSaving` counters told quitting and restore whether to wait. The database ran SQL one write at a time, but each write started from its own task, so a later action could save before an earlier one, and other actions then read stored values behind the screen. Undo was registered with a field or a state object as its target, which the window's undo manager does not keep alive, and which could by then belong to another record.

## What changed

- `LibraryEdit` in `Ure/Features/Edits/LibraryEdit.swift` is a value that says what to change, one case per feature. `LibraryEditor` applies one edit through one service call, so one transaction, and returns what the library now holds and the edit that undoes it. The services now return what a row held before the change, read in the same transaction, such as `Revision<PartRecord>` from `PartService.update`.
- `EditQueue` in `Ure/Features/Edits/EditQueue.swift` is one per library session. The app submits each edit at the moment you act. Before any edit, typing on screen submits first. The queue applies one edit at a time, in that order, keeps each inverse under the change's number, and tells the states what the library holds.
- When an edit fails, the queue stops there. No edit runs past it, so every edit runs on a library that holds every edit before it. Changes made after the failure show on screen at once and wait in order, Undo and Redo included. Try Again runs the failed edit again and then the waiting ones. Discard Unsaved Changes… drops the failed edit and every waiting edit, puts back on screen what the library holds, and clears the Undo and Redo lists, as Revert to Saved does. A cancelled import is your own choice, not a failure, so it does not stop the queue.
- One bar across the top of the record side of the window, `SaveFailureBar`, shows the failure: "Your changes are not saving. They are still on screen and will save in order once Try Again works.", then the reason in one plain sentence, such as "The library couldn't be written to.", and the buttons Try Again and Discard Unsaved Changes…. A database error never shows its SQL on the bar. Its full text is in the bar's help tag. Only the warning triangle is red. The first sentence is semibold in the label colour, and the rest is in secondary gray. The text size and the small buttons are those of the Try Again lines it replaces. Discard asks first: "Discard unsaved changes?", "Everything since the last change that saved goes, and Undo starts over. You can't undo this.", with Discard and Cancel.
- Undo and Redo register on the window's undo manager when you act, with the queue as the target and the change's number as the value. Nothing on the undo stack refers to a field, a view, a state object or a row. ⌘Z goes first to the change's owner, the field or checklist that made it, when it is still on screen. The owner puts back its own text at once and submits that through the queue as a normal edit, under the way back's number, so typing after ⌘Z builds on the undone text, as the old fields did. Typing that has not submitted yet submits before its Undo, so the library has every step. When the owner is gone, such as a deleted part's fields, ⌘Z submits the stored inverse as a new edit, which runs after everything before it. When a new action clears the Redo list, the queue and the owners let go of what they kept for those steps. Typing on a job's add line, which saves nowhere, keeps its own Undo steps on a target the queue owns.
- `AutosaveField`, `FactField` and `ChecklistEditor` only hold typing, and know nothing about failures. They submit after the typing pause, when focus leaves, before any other edit, and when the app asks every field to save. Each burst of typing is still one Undo step. Esc, the "not valid yet" rule and the last good value stay as they were. An edit of theirs that is discarded puts back what the library holds.
- The checklist saves what the screen shows that the library will not hold, as operations that each name one step and only the properties that differ. Each Undo step keeps what its action did on screen, so Undo and Redo put back the steps as they showed, and then save like any change.
- While the queue is stopped and a change waits that the screen shows only once it saves, such as a deletion, an archive or a new part, the record pages take no edits. `EditQueue.holdsRecords` says so, and `WorkshopEditing.canWrite` reads it. During normal saving nothing is held, so a field keeps the cursor while a command saves. Parts typed on a job's add line that wait show under the line as "Not saved yet: …" while the queue is stopped.
- A rule that a change breaks when you make it, such as a second open job for a watch, still shows where you made it, as each state's `refusal`. A rule that only fails when the edit's turn comes stops the queue like any failure, because the edits after it may depend on it. The one exception is an Undo or Redo, which a rule skips, as rule six says.
- Quit, window close, restore and backup export wait through one call, `WorkshopEditing.saveAllFields()`, which is `EditQueue.saveEverything()`. It ends saved, with text that is not valid yet, or stopped at a failure. Quit and window close then ask "Some changes did not save.", with Try Again, Discard Changes and Cancel, in `UnsavedChanges`. Restore and export say to choose Try Again or Discard Unsaved Changes in the main window first, so a backup never leaves out a change.
- Deleted: `ChangeUndo`, every feature's own save task and `isSaving` flag, `PartChangeSide`, `PartStageUndo`, `PartUndoTarget`, `leftFacts`, `pendingWrites`, `MaterialState.pendingChanges` and `removals`, `JobFacts`' `stillWaits` wait, the picker's wait for every field before it discards a blank job, `AutosaveField.flush()` and every `discardUndo`, `saveFactsNow`, `saveAllFacts` and `hasUnsavedFacts` on the states. With the stop at the first failure, also the failure kept for each scope, `retryUndo` and the failed Undo steps the queue kept, each field's own error and failed step, the checklist's own error, the add line's list of names that did not save, the "a field did not save" checks before an archive or a deletion, and the failure line with Try Again under each field, the notes, the checklist, a material title and a part's add line.
- The specification's Editing row, the autosave section and the README now describe the queue and how a failure shows.
- `RestoreStagingTests`' file capture now resolves `/private` paths. On macOS 27.3 the enumerator gives `/private/var/...` while the temporary folder is `/var/...`, so three restore tests failed on the base branch too, before this change. That is a separate commit.

## Design rules

On 6 November, after round nine, the user asked to fix the cause of each group of findings instead of its symptom, and six rules came out of that. After round twelve, the coordinating session saw that about two thirds of all findings needed a failed save first. They came from one rule of the brief: after a failure, later edits still ran. Then the library missed a change while later edits and their Undo steps ran against it, and each round found one more way that Undo, Redo or Try Again brought back the wrong thing. The user chose to stop the queue at the first failed save instead. That makes the library never fall behind the screen, and the six rules became five. Round fourteen then found that changes shown only once they save could leave the screen behind while the queue was stopped, and the user added a sixth rule. Each rule has one place in the code that makes it true, and tests in `UreTests/EditRuleTests.swift` that check it in more than one way.

1. The library never falls behind. Edits run one at a time, in the order you made them, and none runs past a failed one. This replaces old rule 1, "the screen is what counts".
   - The place: `EditQueue.drain` stops at a failure with the failed edit still first, and `EditQueue.retry` runs it again. `ChecklistOperation.changes` works out each move from the order that the moves before it leave, so a save of several moves gives exactly the screen's order.
   - The tests: `noEditRunsPastAFailedOne` and `movesThatWaitSaveTheOrderTheScreenShows`.
2. Undo comes from the stored data. Each edit reads its inverse in its own transaction, and the inverse is right, because the library holds every edit before it. A field or the checklist still shows its own Undo at once, as the action showed on screen, but that change saves through the queue as a normal edit. Typing that has not submitted yet submits before its Undo, so the library has every step. This takes over old rules 2 and 3, and the owners' Redo edits go.
   - The place: `LibraryEditor` reads each inverse, `EditQueue.reverse` asks the owner first and otherwise queues the inverse, and the owners' Undo, in `AutosaveField.undo` and `ChecklistEditor.undo`, submits the step's typing first and then what it puts back.
   - The tests: `undoComesFromTheStoredDataAlsoAfterAFailedSave`, `redoWorksAfterTheOwnerOfItsStepIsGone`, `undoAndRedoPutBackWhatTheActionDidOnScreen` and `undoShowsAtOnceAndSavesAfterTheEditsBeforeIt`.
3. One action is one Undo step, registered when you act. This is old rule 4, unchanged.
   - The place: `EditQueue.submit` and `EditQueue.registerStep`, which the commands, the fields and the checklist call at the moment you act.
   - The test: `eachActionIsItsOwnUndoStep`.
4. The queue keeps what a step needs only while the undo manager holds the step. This is old rule 5, without the failed Undo steps.
   - The place: `EditQueue.retire` and `EditQueue.forget`, which run when Undo uses a step up, when a new action clears the Redo list, and before a restore or after a discard. They tell the owners to forget the step too. A field lets go of its last result once it has saved.
   - The test: `whatAStepNeedsGoesWithTheStep`.
5. A failure shows in one place, with Try Again and Discard Unsaved Changes, and nothing unsaved goes without asking. This is new. Old rule 6, "a failed Undo can be tried again", goes, because a failed Undo is just the failed edit at the head of the queue.
   - The place: `SaveFailureBar` shows `EditQueue.failure`. `EditQueue.discardUnsaved` drops the waiting edits, ends each as discarded so its field or checklist shows what the library holds, and clears Undo. `EditQueue.saveEverything` submits the typing again after each wait, so typing done while quitting waits saves too. `UnsavedChanges.save` asks before quitting and closing, and `BackupState` and `RestoreState` refuse while the queue is stopped. A job being set up that the app throws away when you pick a watch with an open job stays while its fields show text that can't save.
   - The tests: `discardDropsEveryChangeThatDidNotSaveAndStartsUndoOver`, `quittingClosingAndExportingAskWhileASaveFailed`, `savingEverythingSavesTypingDoneWhileItWaits` and `aJobWithTextThatCantSaveIsNotThrownAway`.
6. An edit that could fail for good when its turn comes is refused when you act, not when it runs. "For good" means a failure that Try Again can never get past, unlike a storage failure. Two things carry this out. While a record's deletion or archive waits or runs, during normal saving too, while the queue is stopped, and while Try Again runs it again, that record takes no edits, and every other record and field keeps taking them, so the cursor stays where you type. And while the queue is stopped with a change waiting that the screen does not show yet, no record page takes edits. During normal saving there is no hold for the whole window, because a click must not take the cursor from the field you type in.
   - The place: `LibraryEdit.endedRecord` and `LibraryEdit.usedSpare` say what an edit deletes, archives or uses. `EditQueue.isEnding` and `EditQueue.isUsingSpare` read them from the edits that wait or run, an Undo by the inverse it will apply. `WorkshopEditing.canWrite` reads `isEnding` and `holdsRecords`, and every record page's fields, notes, checklist, add line, material tiles and state pills read `canWrite`. `PartState` refuses its commands for a part that is ending, and offers no spare whose use waits. The parts that wait show under the add line as "Not saved yet: …", without a Try Again of their own.
   - The tests: `aRecordTakesNoEditsWhileItsDeletionOrArchiveSaves`, which saves a deletion, an archive, a material removal and a spare's use slowly, and then a deletion right after Try Again, `recordPagesTakeNoEditsWhileACommandWaitsBehindAFailure`, and `aNameThatDidNotSaveWaitsWithTheNextUntilTryAgain`. The window check types in a job's notes while a part's state click saves, and checks that the notes keep the cursor and every keystroke.

   Every failure that a service can raise when an edit's turn comes, and that depends on an earlier edit, and where the screen prevents it:

   1. A part that is gone, after its deletion or an Undo that deletes it, such as ⌘Z of Add Part. A rename, a fact, a state click or choice, a second deletion, or its use as a spare would fail. The part takes no edits while its deletion waits or runs (`isEnding`), and `PartState` refuses those commands.
   2. A material item that is gone. A title, a second removal, or using it as the cover would fail. Its tile and title take no edits while its removal waits or runs. A second removal and the cover buttons already wait while any material change saves.
   3. A blank job that the app throws away when you pick a watch with an open job. The picker opens the other job, navigation waits while the discard saves, and the job's page takes no edits while it is ending.
   4. An archived watch or caliber. Its facts, notes and material, its cover, and choosing it as a job's watch or a watch's caliber would fail. Its page takes no edits while its archive waits or runs. Its facts already took none while its own archive saved, since W036, and navigation to any other page waits while the archive holds the screen.
   5. "Another job is open for this watch", and a watch that can't take the job. The job state refuses at once with the jobs it knows, and every job command refuses while another job command waits or runs, so two quick clicks on Start Job make one job.
   6. A spare that another line already used. A spare whose use waits is offered to no other line, and a second use is refused.
   7. Waiting text on a job that is no longer Waiting. The job page's facts take no edits while one of its own job changes saves, since W037, and typing submits before the state change.

   One kind of edit can't be refused when you act: an Undo or Redo. AppKit takes the step off its list when you press ⌘Z, before the queue sees it, and it can't put it back. A change that has no Undo step of its own can come after the step and leave it nothing it may do. Start Job is one: after a job is marked Done and another job starts on the same watch, ⌘Z of Done can't reopen the first job. A blank job that goes is another: ⇧⌘Z of its notes has no job to put them on. Codex found this in round seventeen, and the user chose to skip such an Undo or Redo. When a rule refuses it as its turn comes, the queue skips it, says why on the record's page, such as "Nothing was undone. This watch already has an open job. Open that job to continue its repair.", and goes on. The skipped edit changed nothing, so the library is not behind, and the Redo of a skipped Undo does nothing either. A storage failure in an Undo still stops the queue, because Try Again can get past it.

   - The place: `RuleError` in `Ure/Features/Edits/RuleError.swift` lists the errors that rules of the library give. `EditQueue.reverse` marks the edit of each Undo and Redo, also the one its owner submits, and `EditQueue.goesOn(after:_:)` lets such an edit with a `RuleError` pass. `EditQueue.finish` lets go of the step's inverse and puts the message under `EditScope.page`, so notes and a checklist show it on their record's page.
   - The test: `anUndoOrRedoThatARuleRefusesIsSkipped`, with ⌘Z of Done after Start Job, and ⇧⌘Z of a blank job's notes after the job went.

   Not in the list: a checklist step that is gone, because a change of a missing step changes nothing. Storage failures, because Try Again gets past them. Text that a field does not take, because it never submits. And an import's files that could not be added, which are results, as round fifteen's declined finding says.

### Every finding against the new design

The findings from rounds one to twelve, and the regression the window check found, fall into two groups.

These can no longer happen, because no edit runs past a failed one, and nothing keeps a failed change apart from the queue:

1. An Undo whose save failed lost its inverse (round one). A failed Undo is now the failed edit at the head of the queue, and Try Again runs it: `anUndoThatFailedCanBeTriedAgain` and `aNotesUndoThatFailsRunsOnTryAgain`.
2. A field kept an old failed save after a newer one saved (round one), a field told its saves apart by their text (round four), and typing back the saved text kept the failure (round four). A field no longer has a failure of its own. Their tests went.
3. A failed checklist change was lost when a later one saved (round two). The later change now waits: `tryAgainRunsAFailedTickAndThenTheUntickThatWaited`.
4. Try Again of a checklist change lost its Undo step (round three). Try Again runs the same queued edit with its own step: `aTickSavedWithTryAgainKeepsItsUndo`.
5. A local Undo did not finish when the save before it failed (round three). The Undo now waits behind the failed save and runs after Try Again: `undoOfTypingWhoseSaveFailsTakesTheTextBack`.
6. Try Again in the notes did not run the notes Undo that failed (round four). There is one Try Again, for the queue.
7. A failed Undo stayed for Try Again after Redo had used it (round five), and a failed Undo that you left kept its data (round eleven). The queue keeps no failed Undo steps any more. Their tests went.
8. Undo of a failed tick did not save though a later Undo had saved that tick (round seven), and Redo after a change made on top of a failed one did nothing (round seven). The later Undo now waits, so neither case can arise. Their tests went.
9. Try Again submitted the typing from the wrong list (round eight), and Try Again replayed an older tick over a later untick (round nine). Try Again now runs the queued edits in order, and nothing is replayed: `typingAfterAFailedTickWaitsUnderItsOwnUndoStep` and `tryAgainRunsAFailedTickAndThenTheUntickThatWaited`.
10. The checklist kept showing a failure after a later save left nothing unsaved (round eleven). The checklist has no failure of its own any more. Its test went.
11. Redo brought back the library's text instead of the step's after a failed save (round twelve). The library is never behind the screen now: `undoComesFromTheStoredDataAlsoAfterAFailedSave`.

These still could happen without their fix, and their tests stay:

1. The checklist's whole-list save overwrote a waiting Undo (round one), and a tick sent properties that it did not change (round two): `aChecklistChangeMadeWhileAnUndoWaitsKeepsTheUndo` and `aTickWhileTheUndoOfItsRenameWaitsKeepsTheUndo`.
2. Undo could not take back a checklist change that failed (round one), and Undo of one failed checklist change took back others (round three): `undoOfATickThatFailedShowsAtOnceAndSavesAfterTryAgain` and `undoOfOneOfTwoWaitingTicksTakesBackOnlyThatOne`.
3. Esc was not an Undo step of its own (round one): `escIsAnUndoStepOfItsOwn`.
4. A removed material's title still counted as unsaved (round one): `aTitleThatDidNotSaveGoesWithItsMaterial`.
5. Undo of a step you had emptied showed the step twice (round two): `undoOfAClearedStepWhileItHasTheCursorShowsItOnce`.
6. An Undo that waited for the stored inverse did not show at once (round five): `undoShowsAtOnceSoTypingAfterItBuildsOnTheUndoneText`.
7. Redo was lost when Undo took back text that failed to save (round five): `redoBringsBackTextThatFailedToSaveAndWasUndone`.
8. Typing after a failed save reused that save's Undo step (round six): `typingAfterAFailedSaveIsAnUndoStepOfItsOwn`, `typingAfterAFailedSaveThatALaterSaveTookOverIsItsOwnUndoStep` and `tryAgainSavesTheFailedTextUnderItsOwnUndoStep`.
9. The queue and the fields kept texts of steps the undo manager no longer held (round six), and saves that finished after their step was gone stored their inverse again (round eight): `stepsThatANewActionTakesOffTheRedoListKeepNothing` and `savesThatFinishAfterTheirUndoStepWentKeepNothing`.
10. Undo of a blank name offered a Redo that did nothing (round six): `undoOfTextTheFieldDoesNotTakeOffersNoRedo`.
11. A field's Undo saw nothing to save, and its Redo took the text on screen (window check): `twoQuickUndosOfAStateAndItsWaitingTextRunInOrder`.
12. Undo of checklist typing compared the steps as they save (round eight), and typing that saved as nothing lost its Undo (round nine): `undoOfTypingThatSavesAsNothingPutsBackTheStepAsItShowed` and `undoOfTypingThatSavedAsNothingWorksAfterThePause`.
13. Redo of a part's rename was lost when the Undo of the part's addition took the field away (round eleven): `redoWorksAfterTheOwnerOfItsStepIsGone`. It now works from the stored data, because the typing submits before its Undo.
14. Several moves saved the wrong order (round twelve): `movesThatWaitSaveTheOrderTheScreenShows`.
15. A part whose deletion waited behind a failure could still be renamed, and Try Again then stopped at a rename that could never save. Parts added while the queue was stopped vanished until they saved (round fourteen). The same rename was possible while a deletion saved slowly, or right after Try Again (round sixteen). Rule six covers all three: `recordPagesTakeNoEditsWhileACommandWaitsBehindAFailure`, `aRecordTakesNoEditsWhileItsDeletionOrArchiveSaves` and `aNameThatDidNotSaveWaitsWithTheNextUntilTryAgain`.
16. A part's name on its job's page read only the job's permission, so it could be renamed while its deletion saved, and Redo of Use Spare did not count as a spare in use, so the spare was offered twice (round seventeen). Rule six now covers both: the window check of a slow deletion, and `aSpareThatRedoPutsBackOnAJobIsNotOfferedAgain`.
17. ⌘Z of Done after Start Job on the same watch stopped the queue for good (round seventeen). The rule now skips it: `anUndoOrRedoThatARuleRefusesIsSkipped`.

## Tests

The existing behaviour tests were ported to the queue and all kept, except where a test checked a fake save closure's list of saved texts. Those now check the stored values in a real library, which is the behaviour they described. The field, notes and checklist editor tests now run against a real library and receive Undo results from the queue, as the screens do.

The queue tests in `UreTests/EditQueueTests.swift`:

1. `editsOfEveryKindRunInTheOrderTheyWereSubmitted` holds the library and submits seven edits of six kinds, each of which only works after the one before, such as a waiting text that needs the job to be Waiting. They finish in the order submitted and all save.
2. `undoAndRedoKeepTheOrderYouActedInWhileSavesWait` adds a part and renames it, then presses ⌘Z twice while the library is held. The rename's Undo runs first, then the addition's. Redo twice, also held, gives both back. Then the Undo steps can be forgotten, as before a restore.
3. `aFailedEditStopsTheQueueAndTheEditsAfterItWait` makes watch writes fail. A typed owner fails, and a caliber change and a part after it wait. Try Again while writes still fail keeps the queue stopped, and the next Try Again saves all three in order.
4. `savingEverythingWaitsAlsoForAChangeMadeWhileItWaits` starts quitting while the library is held and typing waits, adds a part after that, and checks that quitting goes ahead only once both saved.

The same file keeps one test for each Codex finding whose case can still happen, as "Every finding against the new design" lists.

One regression test for each bug class, in `EditQueueRegressionTests`. Each was also written against the old API and run on `aebd6c2`:

1. Typing went into the previous caliber after switching records: `typingStaysWithTheRecordItWasTypedOnAfterSwitching`. Passes on the old code, because the old bug was in the view's reuse of an AppKit field, fixed in W035. The window check below drives the real fields for it.
2. Two quick ⌘Z presses undid a job's state and its waiting text out of order: `twoQuickUndosOfAStateAndItsWaitingTextRunInOrder`, with the library held during both. Passes on the old code, which W037 patched.
3. A spare used after two typed parts took the second part's place: `aSpareUsedAfterTypedPartsKeepsItsPlace`, through the add line while the library is held. Passes on the old code, which W040 patched with one parts queue.
4. Quitting went ahead while a second change was still saving: `quittingWaitsForASecondChangeStillSaving`, two queued Undo steps of archives. Not run on the old code, because the old quit refused while a change saved instead of waiting, and its per-state flags had a gap between two queued changes that a test can't hit on purpose.
5. ⌘Z after an undone part deletion would likely crash: `undoAfterAnUndoneDeletionReachesTheTypingBeforeIt`, with no field kept alive. Passes on the old code, which W040 patched with `leftFacts`.
6. An action read a stored value behind the screen, such as Mark as Bought's stale price: `aChangeSeesWhatWasTypedJustBeforeIt`. Notes and a material title typed just before archiving a watch save before the archive, and a job being set up keeps a title typed just before a pick would discard it. **Fails on the old code**: the archive saved first, then the notes and the title failed with "This record is archived", and were left unsaved on a page that can't change.

So five of the six bug classes had been patched one by one before this change, and their tests pass on the old code. The sixth had not, and its test fails there. The queue now prevents all six in one place.

### Local window checks

This Mac gives sessions no Screen Recording or Accessibility permission. As accepted for the Rework stories on 5 November 2026, local-only tests hosted the app's real `LibraryRootView`, with every session environment and the bridged toolbar, in a window of the test host, and drove the real views. They were never committed and never run on CI. The last run was on `d7a2b91`, the commit with the skip. On its first run the sidebar check found the search field not focused after ⌘F in Parts, Watches and Calibers. It passed when run again on the same build, and the queue does not touch focus, so that was the test window's focus timing.

A new check, `LocalEditQueueAppCheck`, drove the six bug cases through the real fields and the session's own commands:

1. It typed "Omega" in one caliber's maker field, switched to the second caliber before the typing pause, and typed "ETA" there. Each caliber held its own maker. ⌘Z took back "ETA" on the second caliber, and the next ⌘Z took back "Omega" on the first.
2. It set a job to Waiting, typed "a crystal" as the waiting text, and set the job to Done while the text was still being typed. With the library held, it pressed ⌘Z twice. Both ran in order once the library let go, which left the job Waiting with no waiting text and no failure. ⇧⌘Z twice gave Done back.
3. With the library held, it typed "Mainspring" and "Hairspring" on the job's add line, each with Return, and then used the spare "Crystal 30.0 mm" through "crys", the Down Arrow and Return. The stored order was Mainspring, Hairspring, Crystal 30.0 mm.
4. It renamed Mainspring to "Mainspring 1.10" and deleted the part. ⌘Z brought the part back with its new name, and the next ⌘Z reached the rename and gave back "Mainspring". ⇧⌘Z twice deleted it again with no failure.
5. It typed "Crown tube replaced." in a watch's notes and "Supplier page" as a link's title, and archived the watch before the typing pause. The notes and the title saved, the watch was archived, and nothing was left unsaved.
6. It typed a new job title, moved a part on to Fitted while the library was held, and closed the window. The window stayed open while the changes waited and closed once both had saved.

It also checked the parts of the design that came after the brief:

1. It typed in a job's notes while a part's state click saved, and the notes kept the cursor and every keystroke. While a part's deletion saved slowly, that part's name field took no edits, and the other part's name did.
2. It made job writes fail and typed a title. ## Design rules that changed

Three of the brief's rules were changed as the work went on.

1. The brief said that later edits still run in order after a failure. The user replaced that after round twelve: the queue stops at the first failed save. Most findings came from that rule.
2. The brief said that Undo comes from the stored data. It still does, but a field or the checklist shows its own Undo at once, and that change saves as a normal edit. An Undo that waits for the stored inverse can't show at once, so typing after ⌘Z built on the old text, which the old fields never did (round five).
3. Checklist edits are operations on single steps instead of the whole list. A whole list submitted by one change overwrote an Undo or a change that was still waiting (rounds one and two).

## Accepted corner cases

The user accepted these on 6 November, as the app's main user. Each is one line.

1. A skipped Undo leaves the Undo list, so after the second job closes, ⌘Z can't reopen the first job, and you set its state by hand.
2. The Redo of a skipped Undo does nothing, because nothing was undone.
3. During a slow save, only a record whose deletion or archive is saving stops taking edits, so a run-time rule failure that rule six's list misses would stop the queue, and only Discard gets past it.
4. A failed disk write stops the queue until the disk works again, and the only other way on is Discard, which drops every change since the failure.
5. The message of a skipped Undo of a gone job's notes or checklist shows on the job page you have open, which can be another job's page.
6. An import whose files could not be added counts as saved and does not stop the queue, as round fifteen's declined finding says.
7. The skip itself had no Codex review, because round eighteen was stopped.
